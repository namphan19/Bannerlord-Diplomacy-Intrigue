## 1. User story

> **As** a player who has set the game to one of its own languages,
> **I want** the mod's screens, prompts and messages to switch to that language with the game,
> **so that** I can read what a treaty, a grievance or a mission will cost before I pay it.

> **As** a community translator,
> **I want** to copy one folder, change its name and translate one column,
> **so that** I can ship a language without touching the mod's code.

## 2. Why

Today `ModuleData/Languages/EN/std_module_strings.xml` holds two strings. About **1,300**
player-facing literals (42k lines, 2026-10-03 count) sit in code and prefabs with no key, so no
translation can reach them. The mod's prices, odds and bands are the point of the design; a player
who cannot read them cannot use the mod. The game already offers 13 languages, and a player who
has chosen one expects every mod to follow it.

## 3. Scope

**In**
- Every string a player can see: Gauntlet prefabs (Realm, Court, Intelligence tabs, Encyclopedia
  court page, peace table), view-model text, inquiries, notifications and log-to-screen messages,
  tooltips, MCM setting names and descriptions, the main-menu warning, the Nexus/Workshop copy.
- `EN` as the complete source file set, and a translation for each of the game's own 13 languages
  (ST-8): `EN`, `BR`, `CNs`, `CNt`, `DE`, `FR`, `IT`, `JP`, `KO`, `PL`, `RU`, `SP`, `TR`. Read from
  `Modules/Native/ModuleData/Languages` on the installed game (2026-10-03), **minus `VI`**: that folder
  is a community Vietnamese patch, not the game's (its files date from 2026-07-12, while the official
  languages were rewritten by Steam on 2026-10-02, and it needs the `FontVietHoa` mod's font).
- A check that fails the build when a converted area regresses (ST-6).
- A one-page guide for community translators (ST-9).

**Out**
- **Log lines, telemetry, `diplomacy.*` command names and their output, exception text.** These
  are for the lead and for tools such as `analyse-log.py`; they stay English.
- Design docs and code comments (English by CLAUDE.md §4).
- Vietnamese, which the game does not offer: [story 4.2](4.2-vietnamese.md).
- Any other language the game itself does not offer. The mod follows the game's language setting and adds
  no selector of its own.
- Right-to-left layout (the game offers none) and font work: the CJK languages use the game's own
  fonts, which ST-1 confirms for a mod's strings.

## 4. Business rules

| # | Rule |
|---|---|
| R1 | **Source form.** A translatable string is `new TextObject("{=DI_<area>_<slug>}English text")`, with the English as the fallback. A missing key degrades to English, never to a blank or a raw key |
| R2 | **Keys are stable identifiers, not text.** A wording fix keeps its key; a change of *meaning* gets a new key, so no translation silently says something the English no longer does |
| R3 | **No sentence is built by joining fragments.** A sentence with a number, a name or a term is one string with named variables (`{AMOUNT}`, `{KINGDOM}`), so word order can change per language |
| R4 | **Variables are validated.** Every translation carries exactly the `{VARIABLES}` its English source has |
| R5 | **No hidden text.** A number shown in the UI is still the number the AI used (CLAUDE.md §3); translation changes words, never values or rules |
| R6 | **No throw crosses the engine.** Text lookup failing answers the English fallback and logs once |
| R7 | **English must not change.** With the game in English, every converted surface reads exactly as before (AC1) |

## 5. Acceptance criteria

**AC1 — English is unchanged**
- Before the conversion, record every converted surface's English text (a golden file from the
  extraction tool, plus screenshots of the Realm, Court, Intelligence and peace-table screens).
  After: the same text, character for character, in the same screens.

**AC2 — A second language really switches**
- With a vanilla language selected in the launcher, the converted screens show it, and switching
  back to English restores English. Checked on three: `DE`, `RU` and `CNs`. With a key deleted from
  one language's file, that one string shows English and nothing else changes.

**AC3 — Prefab text is covered**
- Every visible string in `GUI/Prefabs/**` is either behind a key or listed, with the reason,
  in ST-1's findings. No panel mixes languages.

**AC4 — Variables survive**
- A string with `{AMOUNT}` or a name renders the real value in both languages. A translation with
  a missing or extra variable fails ST-6's check.

**AC5 — The guard holds**
- `check-localization.ps1` (ST-6) fails on: a duplicate key, a key in code with no `EN` entry, an
  `EN` entry used nowhere, a variable mismatch between languages. `build.ps1` and `deploy.ps1` run it.
  `check-save-ids.ps1`, the `Harmony patched N methods` line and the save-data ids are unchanged.

**AC6 — Fit**
- The screens are checked in game at the shipped resolutions in the longest language (`DE` or `RU`)
  and a CJK one (`CNs`): no clipped button, tab or tooltip, and no missing glyph. Anything that does not fit is fixed in the translation first, the layout second.

**AC7 — A translator can start**
- A person who has never seen the repo can fix or improve one language from the guide alone (ST-9),
  tested by following it once from scratch on a copy of one language folder.

**AC8 — Release**
- `release.ps1`'s zip and the Workshop stage contain every `Languages/*` folder. The Nexus and
  Workshop pages say which languages ship and how to add one.

## 6a. How a language is tested

**Corrected 2026-10-04. The version this section used to carry does not work.**

What it used to say, and what is wrong with it: that the setting is the first line of
`Documents\Mount and Blade II Bannerlord\Configs\BannerlordConfig.txt`, `Language=<id>`, and that
you write it and start the game. Writing `Language=Deutsch` and starting through `games_start`
changes nothing: the game rewrites the line to `Language=English` as it starts (the file's
timestamp is the launch second). The game is then in English, the mod's screens included.

What was checked before saying so:

| Where the language could live | Result |
|---|---|
| `BannerlordConfig.txt` line 1 | rewritten to English at every startup - it is an output, not the setting |
| `LauncherData.xml` | no attribute containing "lang" at all |
| the in-game Options screen | tabs are Video, Performance, Audio, Gameplay, Mod Options, Keybindings - **no Language** |
| a console command | `list_commands` on `lang` and on `locale`: none in v1.5.3 |
| the registry under `HKCU\Software` | no TaleWorlds / Mount and Blade / Bannerlord key |
| everything else under `Documents\Mount and Blade II Bannerlord` | no file but the config mentions Deutsch or Vietnamese, and it is the config |

So the language is owned by the **official launcher's UI** and reaches the game from there
(CLAUDE.md §1: the launcher hosts the game in its own process). A `games_start` / BLSE Standalone
launch bypasses that UI, so it comes up English and there is nothing on this machine that can change
it from inside the game.

**How to test a language, now that it is known to work (2026-10-04, from the lead's session):**

1. `pwsh ./scripts/localization-fixture.ps1 -Action Write` - fourteen German keys into the
   **deployed** `Languages/DE/di_strings.xml`. It refuses to write a key that `EN` does not have, or
   whose `{VARIABLES}` differ, so the fixture cannot drift from the code. `deploy.ps1` overwrites
   that folder, so run it again after a deploy.
2. Change the language to Deutsch **in the official launcher**. The game is already running, or start
   it - **no restart is needed**: the game reloads every module's strings when the language changes
   (the log shows the whole set reloaded between 11:15:43 and 11:15:46).
3. Open the Realm tab and the Court tab. `Realm` reads **Reich**, `Court` reads **Hof**, the Court's
   heading reads **Der Hof**, *Court blocs* reads **Phe des Hofes**, *Our claims* reads **Unsere
   Ansprüche**, *Our agreements* reads **Unsere Vereinbarungen**, *Tribute, per period* reads
   **Tribut je Zeitraum**, *entitles land* reads **berechtigt zu Land**, *ages out in 172 days* reads
   **verfällt in 172 Tagen**, and *one kingdom answers to Northern Empire* reads
   **ein Königreich gehorcht Northern Empire** - which is the same value in a different word order,
   the point of R3. *Write a report to file* reads **Bericht in Datei schreiben**.
4. One key is **left out of the fixture on purpose**: `DI_REALM_ONE_KINGDOM_ANSWERS_TO_YOU_2`. AC2
   also asks that a single missing key shows English and changes nothing else, and that is what it
   should do.
5. `pwsh ./scripts/localization-fixture.ps1 -Action Remove` puts the repo's empty file back.

**The proof is in the game's log, not in a screenshot.**
`C:\ProgramData\Mount and Blade II Bannerlord\logs\rgl_log_<pid>.txt` names every language file the
game opens, per module. It is how the mod's `DE` folder was confirmed to be read, and it is the
first place to look for any language question - including which language the game thinks it is in.

The rest of the rule still stands, written 2026-10-03 after the lead reported that an earlier dev
left the game on English and then tried to turn the mod's text into Vietnamese by hand. The mod's
text is never changed to test a language. The game's language is.

- **Write down the original value before the first test and put it back after the last.** The lead plays
  on this machine. Do not leave it on a language the lead did not choose. (2026-10-04: the file
  reads `Language=English`, which is what it read before, and the game puts it back itself.)
- Do not edit `EN` or any source string to see another language: that tests nothing, and it is what
  turns an English source into a translated one that nobody can build again.
- The English source stays in code and in `EN`. A translation lives only in its own language folder.

**Definition of done**
- Every AC marked verified live, verified by compile only, or not verified.
- No save data, no Harmony patch.
- Telemetry, log and `diplomacy.*` output untouched and still English.

## 9. ST-1 — findings

**Read from the installed game and from the game's IL, 2026-10-03. The game was not started.**

**(a) The language folder, per language.** Mods ship `ModuleData/Languages/<code>/`, each folder
holding a `language_data.xml` and its strings files. Vanilla's own `language_data.xml` for a
language lists its files the same way, and 284 per-language `language_data.xml` files ship across
the installed modules. Four of ours (ButterLib, Harmony, MCM, UIExtenderEx) are the model, and
**they all have an `EN` folder with a `language_data.xml` too** - so English is a folder like any
other, not a special root case. Ours are generated with the `id`, `name`, `subtitle_extension`,
`supported_iso` and `text_processor` **copied byte for byte from the installed Native module**:
`Русский`, `Türkçe` and `Español (LA)` are not ASCII, and a mistyped id is a folder the game
silently ignores. Written with a UTF-8 BOM, as the game's own files are.

**(b) Prefab text CANNOT be keyed. This is the finding that resized the story.** Read from the IL
of the installed assemblies, no session needed:

- `TaleWorlds.GauntletUI.BaseTypes.TextWidget.set_Text` compares against `Text.get_Value` and calls
  its own `SetText`, which sets `TaleWorlds.TwoDimension.Text.CurrentLanguage` and `.Value`.
- `TaleWorlds.TwoDimension.Text.set_Value` passes the string straight to `TextParser.Parse`.

Nothing on that path reads a localization key. A widget's `Text` is a plain string, so
`Text="{=DI_x}English"` in a prefab would be drawn as the literal characters `{=DI_x}English`. No
vanilla prefab does it either: **0 of 1,006 prefab XMLs in the install key a `Text` attribute**,
and the ones that hold text at all bind `Text="@Property"` to a view model. So every static label
in our 12 prefabs - **92 of them** - has to move into a view-model property returning
`DiText.T(...)`, with the binding becoming `Text="@Property"`. ST-4's prefab strategy is
therefore "move text into view-model properties", exactly the fallback the story allowed for, and
it is the one part of the conversion not done (below).

The other half of the same finding is what *does* resolve: `TextObject.ToString()` calls
`MBTextManager.ProcessTextToString`, which asks `GetLocalizedText(id)` and, when that comes back
empty, processes the default text after the `}`. So `{=key}English` in **code** resolves, and a
missing translation degrades to English by the engine's own path (R1), not by a fallback we wrote.

**(c) MCM's text for settings.** `SettingPropertyBool("Diplomacy", …, HintText = "…")` - MCM's own
strings live in `Bannerlord.MBOptionScreen/ModuleData/Languages/<code>/sta_strings.xml`, keyed by
the setting's own display text, and MCM resolves them through the same game localization. We do not
need MCM's mechanism: a setting's name and hint are ordinary C# strings, so they go through
`DiText.T` like everything else. Only the first positional argument and `HintText` are text; the
rest are the value's bounds and its number format (`SettingPropertyFloatingInteger("War exhaustion
rate", 0.25f, 4f, "0.00")` has three words in it and only the first is a sentence), and
`tools/Localize` was taught the difference after a dry run offered to key `"0.00"`.

**(d) MCM's setting names and hints cannot be keyed at all.** `[SettingPropertyBool("Diplomacy",
HintText = "...")]` - an attribute argument has to be a compile-time constant, so there is nowhere
to put a `DiText` call. These 18 strings stay English in every language. Translating them would
mean adding entries to *MCM's* own `ModuleData/Languages/<code>/sta_strings.xml`, which lives in
another module's folder; whether MCM looks a mod's setting up by its display text was not
verified, so no route is claimed here.

**Still to do, and it needs the launcher, not a session:** switch the game's language and look.
Attempted 2026-10-04 and it does not work from a `games_start` launch - §6a has what was checked.

### What the first session found (2026-10-04)

ST-7 was the sub-task that could only be done by starting the game, and it earned its place: **four
defects, none of which any check in the repo could see**, and a fifth that a check can now block.

**1. Every key was drawn raw. `DiText.O` built the wrong string.** It read
`new TextObject("{" + KeyPrefix + "}" + key + "}" + english)`, which is `{DI_}DI_REALM_REALM_2}Realm`,
not `{=DI_REALM_REALM_2}Realm`: the prefix sat inside the braces instead of in front of the key, so
the engine read a token with no sigil and no id. The Kingdom screen's tab strip drew

> Clans · Fiefs · Policies · Armies · Diplomacy · `{DI_}DI_REALM_REALM_2}Realm` · `{DI_}DI_COURT_COURT}Court`

Rules 1-7 all passed, because they read the key and the English as two literals and never built the
string the engine is handed. **Rule 8** now refuses a `Core/DiText.cs` that does not spell the sigil
`{=` as a literal, and no file may contain the string the mistake produces. It was run against the
pre-fix file (fails) and the fixed one (passes), so it is a guard that has failed once on purpose.

**2. Three labels came out of the conversion with the wrong character.** The Intel tab's odds legend
and skill row, and the Diplomacy tab's note about the game's own rows, had **U+00A7 SECTION SIGN**
where the prefab had **U+00B7 MIDDLE DOT**. The session note already recorded that PowerShell 5.1
damages non-ASCII; these three survived it because the damage was *silent* - a different character,
not the U+FFFD that gave the other nine files away.

**3. The Court panel's heading became "Court"**, which is the tab label's text *and* its key: the
prefab said "The court". Two sentences, so two keys (R2). It is `DI_COURT_THE_COURT` now; the tab
keeps `DI_COURT_COURT`.

**4. Enum names were reaching the screen as text.** The Realm tab's claim list drew
`ReclaimAncestralLand`, and the Diplomacy tab drew `DefensivePact`, `NonAggressionPact` and
`TributaryPact`. An enum name cannot be translated - a translator is handed a value, not a word -
and it reads as a bug on a screen. `CasusBelli.NameOf` now gives the nine justifications as keyed
words and three call sites use it. STATUS.md said on 2026-10-01 that treaty names no longer show the
enum; that was true of the call-to-arms inquiry and not of the Diplomacy tab.

**5. `tools/Localize` did not see a qualified `DiText` call.** `CasusBelli.cs` writes `Core.DiText.T`,
the way it already writes `Core.ModState`, and `Calls.Name` returns a member access verbatim - so
`emit` left nine keys out of the English file, and the idempotence guard would not have recognised
those calls as already keyed, meaning the next `rewrite` would have keyed them a second time. Two
readers of the same call have to agree: `Calls.IsDiText` now matches the tail of the name. The key
count went 644 -> **653** because of it.

**The method that found 2, 3 and 4 is worth repeating.** It was not reading a screen. Every literal
that moved out of a prefab was read back out of `git show 79a5c96:<prefab>`, matched to the property
that replaced it by line number, and compared with the `DiText` English behind that property: 88

### §9a. What the second pass found: the tool's own dry-run list was wrong

**2026-10-04.** The 122 candidates the tool offered had been deferred because an earlier sample of
them looked wrong. Reading all 122, by eye, showed the sample was right and the tool was wrong.
Three of its rules had to be fixed before any of it could be applied, and one of them would have
**deleted English from a screen**.

**1. A conditional the tool would not rewrite was treated as a value.** `SupportsChoices` counted
the conditionals it could rewrite and, when a conditional was left over, the loop only looked for
another conditional *nested inside* it. A conditional sitting in the part itself fell through, and
the part became an opaque `{VARIABLE}`. The text went with it:

| the code says | the report offered | what the player would have seen |
|---|---|---|
| `Clan {NAME}, the crown` / `Clan {NAME}, {MOOD}` | `Clan {NAME}{TOLOWERINVARIANT}` | "Clan Sturgia" - the crown, or the mood, gone |
| `Speaks through {LEADER}` / `Speaks through nobody` | `Speaks through {TOSTRING}` | "Speaks through nobody" impossible |
| `...can grow to {CEILING}; it stands at {NOW}.` | `...can grow to {CEILINGOF}{TOSTRING}` | the clause after the number gone |

`IsTextBranch` is what declined these conditionals - a branch that is itself a concatenation, or
that is punctuation only, or a value. The rule now is: **a conditional the tool will not rewrite is
never a variable**, and the site goes by hand.

**2. A variable could be carrying English.** R5 lets a *value* travel as a `{VARIABLE}`, and the
value is a number or a name. Three shapes broke that and the tool keyed all three:
`var verb = leader == Hero.MainHero ? " are " : " is ";` would have made `{WHO}{VERB}held - 3 of 30
days` a key; `SideChange.SideName(...)` behind `{SIDE}`; and `TreatyRegistry.Sign(..., out var
reason)` behind `{REASON}` - a whole refusal sentence. A key there reads half in one language and
half in another, and no translation of the surrounding words can fix it. `EnglishBehindVariables`
looks one hop through the locals of the enclosing method and at the `out` names in it, which is
enough for every one of these and stops there on purpose: a second hop is dataflow analysis, and a
wrong answer from one would put an English word inside a translation.

**3. The shape rules ran before the boundary rule.** `ShapeVerdict` was called before the tool
decided whether a string reached a screen at all, so a telemetry row or a log line that happened to
have an awkward shape was relabelled `manual` - "a human has to write this". That is what inflated
the backlog to 318, and it is why the count above is **162** and not 440. The rules now run last,
and only for something already judged player-facing.

**What the shape rules cannot reach is written down.** Six sites in `DiplomacyMenu` carry a refusal
sentence the method only *receives* - `out var reason` written on an earlier line - and one hop
does not take that far. They are in `exceptions.txt` by method **and wording**, because every one of
those methods also holds strings the tool keys correctly (`DefectToAttacker` has "Kneel to {NAME}"
right beside "Cannot defect: {REASON}") and a whole-method rule would take those too.

**And the first anchor chosen for them was the wrong one, for a reason worth keeping.** They were
written as `Method:line`. Applying the rewrite inserted lines above them, and all six rules stopped
firing in the same minute - the sites went back into the convert list with nothing to say why, and
the next `rewrite --apply` would have keyed every one of them. **A tool that moves lines cannot have
its judgements anchored on lines.** They are anchored on the English the tool computed, which no edit
above them can move; if the wording changes the rule stops matching and the site reappears in the
report, which costs nothing. Two details that took finding: the exemption has to be read *after* the
whole template is built, because the skip-reason chain runs earlier and sees only the first literal
(`"Refused: "`, not `"Refused: {REASON}"`); and a rule is one line, so a sentence that breaks across
lines writes its breaks as `<br>`.

**The method.** The dry-run list is not evidence because the tool produced it; it is a list of
things a tool wants to do, and one of its rules was silently deleting text. It was read against the
source for every shape that looked odd, and the rule fixed only when the source proved it wrong.

### §9b. The producers, and the second live enum defect (2026-10-04, later)

Fixing §9a's rules turned 23 sites from "a variable holding English" into "listed in
`text-producers.txt`". Reading that list against the source is what found the rest of this section.

**1. The producer list had never worked, so the tool hid work instead of finding it.**
`TextProducers.IsTextProducer` compared `src/<module>/Diplomacy/ExhaustionBands.cs|Name` against a
set that `Load` had reduced by stripping the module directory. Not one entry ever matched, and a
miss reads "not a screen: outside UI/, no sink, and no text-producing method" - which is what a
genuine log line looks like. The five exhaustion band names and the five band meanings were
therefore reported as log text, and this story claimed they were converted. **They were not.** A
wrong rule shouts; a lookup that cannot return true is silent, and it hides work rather than
inventing it. The first fix spelled the module directory wrong in a constant - `Intrague` for
`Intrigue` - and produced the same symptom, so `Tail` now cuts at the last `src/` and drops one
directory, with no spelling in it at all.

With the list working, 69 more literals became candidates and **every one was real**: band names and
meanings, the six office titles, the thirteen grievance titles, the loyalty and crown bands, the
eight mission types, the treaty-enforcement reasons. Thirty were keyed or keyed by hand. Two whole
methods were held back in `exceptions.txt` and are still to do: `Power.Describe`, whose line is
assembled from a share plus a band clause with `"; "` in C# - a key per fragment is a key per word -
and `PeaceTable.DescribeAllowance`, whose price rows carry their column alignment **inside the
string** (`"town"` followed by fourteen spaces). That padding is layout, and no translation can keep
it; it has to move into the prefab's alignment first, which is Kingdom-UI work.

**2. A second live enum-on-the-screen defect, in eight places.** `Treaty.Type` stringifies to its
member name, and eight call sites wrote `+ treaty.Type +`: both call-to-arms announcements, the
inquiry's refusal paragraph, two Diplomacy notifications, the war row's blocking reason, Hegemony's
bound list, and two `type.ToString()` fallbacks. The same class as §9's defect 4, which was fixed for
`CasusBelli` and `VassalTribute` and missed here. `Treaty.NameOf(TreatyType)` now names the six kinds
behind keys, in one place - `RealmVM`'s private copy is gone - and the live run shows **"the
Vassalage with Northern Empire forbids it"** where the row used to print `TributaryPact`.
`Treaty.ToString` keeps the enum on purpose: that string is for the log and the telemetry, and a
translated word there would break `analyse-log.py`.

**3. Two more clauses of English travelling as `{VARIABLE}`.** `CallToArms.RenounceClause` returned
a finished English clause and both the call-to-arms inquiry and the summons inquiry wrote it into
`"{CLAUSE}"` behind an "and" the translator cannot see. Each is now a whole keyed sentence, three for
the call to arms and two for the summons, and the shared clause is deleted.

**Checked live, all three tabs, 0 ERROR / 0 WARN, `Harmony patched 7 methods`.** Realm: the Hold row
reads `hold 29 (at breaking point; counting down to revolt)` - a keyed pattern over two keyed words.
Court: the offices read `Envoy / Steward / Treasurer / Spymaster / Watch`, the offices' standing
reads `Envoy you (Charm 0) against Dachan (Charm 162)`, and the grievance ledger reads **"Their
candidate for the throne passed over"** where it used to print `SuccessionPassedOver`. Diplomacy:
`Vassalage` and `Tributary pact` as words, and `the Vassalage with Northern Empire forbids it`.
The two pre-existing layout overlaps are unchanged and still not localization.

**What this changed in the numbers.** 834 keys after the producers, **852** after the eighteen the
tool keyed. The backlog moved 162 -> **166**, *up*, because the path fix surfaced honest work that had
been hidden rather than done: a count that rises when a tool gets better at seeing is the count
getting honest, and that is the right direction.
